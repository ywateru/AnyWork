# WorkBuddy visible transcript and live request snapshots

Two independent projection bugs explained the reported behavior in WorkBuddy Desktop 5.9.3.

The native `ConversationHistoryQueries.requests` implementation passes `beforeRequestId === undefined` into `pageByIds` to include the current assembler. AnyWork sent JSON `null` on its latest-page request. That selects the historical page without current assembler requests. Latest-page and child queries now omit the cursor field; older pages retain the exact native cursor. Reading snapshots does not change native selection/subscribers, refresh the desktop through `get`, send prompts again or start an engine.

The passive JSONL reader also treated runtime prompt text as visible user text. Native records can contain a generated sequence of `<system-reminder data-role="user-context">` and `additional-data` blocks followed by `<user_query>`. The native transcript projector decodes these into visible user content. AnyWork now decodes only a complete, known native envelope with native provenance (`startsNewUserRequest:true` or `input_text`). The inner user query is preserved verbatim, including user-authored reminder tags. Arbitrary canonical display text is never processed by an XML-stripping regex. Native canonical snapshots already select `sourceContentBlocks` where supplied by native send options; AnyWork consumes that display representation and excludes native `_meta.isMeta` / `_meta["codebuddy.ai"].isMeta` blocks while preserving visible text and attachments.

Already imported user rows have stable source keys. Ordinary event replay deduplication therefore kept the original dirty row even after a clean native snapshot arrived. WorkBuddy user snapshots now reconcile only the exact owning WorkBuddy user event: update its visible text, display text and input in place, or remove a proven meta-only row without creating an empty user bubble. A transactional `history/reset` prompts existing clients to refetch. Native request identity, sequence, client identity, assistant events and pending approvals remain intact. A previously validated live display cannot be overwritten by a lagging passive transcript. Partial or failed source reads retain the existing history and existing branch-safety rules.

## Verification and limits

Focused adapter and Store tests cover cursor omission/preservation, native display metadata, visible literal reminder tags, strict generated framing, stable-key legacy-cache repair, pending/assistant preservation, meta-only removal, repeated polls and live-over-passive precedence. The shared-history HTTP fixture seeds an older dirty cached row then reopens it, checking repaired text, display text, raw input and original sequence alongside existing malformed/partial/branch retention tests.

The CDP carrier fixture models the native null-versus-undefined boundary, incremental native replies and desktop-originated updates. It exercises the real HTTP server and SSE; browser checks use built AnyWork assets rather than API response mocks. A deterministic preload fixture demonstrates adapter behavior but does not claim an actual new prompt was sent to the installed WorkBuddy. Installed-application acceptance here is passive snapshot comparison only. Other WorkBuddy versions and unknown runtime-envelope shapes remain outside the pinned decoder's coverage.

Validation on this candidate: server unit suite **115 passed / 4 opt-in ignored**, focused WorkBuddy subset **20 passed / 3 opt-in ignored**, Clippy all server targets with warnings denied passed, and the real HTTP shared-history suite passed. The extended CDP carrier with built Web/PWA assets passed its existing transport/control cases plus actual-browser same-key legacy repair over SSE, web-composer incremental reply/completion, desktop-originated incremental reply/completion without an extra send, meta-only prompt hiding without an empty bubble, and repeated-poll idempotence. All prompts in these checks target the deterministic isolated fixture, never the installed WorkBuddy.
