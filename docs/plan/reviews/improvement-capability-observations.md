## Authority, safety and delivery boundaries

The separation into SDK transport evidence, Runtime installation identity, adapter peer identity and native-instance/version evidence is appropriate. It prevents an AnyWork UUID, manifest version, desktop stream v11, a cached history sequence or a valid descriptor from becoming an invented native boot/version proof. Expiry and closure are independent of stored status. A pure read cannot create observations, probe native state, update persistence or keep stale readiness alive merely by being read.

I07 is proposed as the single owner of volatile connection bindings and invalidation. I03 consumes that binding and owns recording gaps/reconciliation; I02 retains persistent message/preparation/native-ID/dispatch/result fences. The proposal neither copies a message journal into observations nor treats a reconnect, idle snapshot, new peer or recovered Store as permission to resend ambiguous work. Manual/automatic responses and other control operations retain their adapter guards and require their own durable-recovery contract if that behavior is later added. The analysis does not claim accepted I02/I05 source already implements full I03.

The recommended first slice is defensible: lifecycle correctness and old-generation isolation, with native `allowed_now` still false and old Web behavior unchanged. Typed critical errors and projection/Web activation are separate slices; I02b owns message preparation/dispatch integration. Static evidence from code or fake-native tests cannot close WorkBuddy's experimental real-writing acceptance or other platform/topology gaps.

## Nonblocking clarification and b1 contract prerequisites

1. **Keep `native_instance` terminology consistent.** Section 4.5 permits “opaque connection-binding or unknown” for the public native-instance field, while sections 6.1 and 8 correctly recommend retaining its native-instance meaning and naming a local connection binding separately. Prefer the latter wording throughout. A generated connection UUID must not fill a native boot-identity field. The rest of the document already enforces this conservative interpretation; it is not a blocker to accepting the analysis.
2. **Make the next b1 contract concrete before coding.** Choose singleflight or a nonforgeable qualification token; specify map/peer/gate/Store lock ordering, attach-time staging versus installation, setup cancellation cleanup, and compare-and-commit points across awaits. A preliminary equality check followed by an unguarded later effect is insufficient. Cross-session aliases of one native thread remain coordinated with I02/I11 rather than silently “solved” by a per-session lock. The document identifies these choices but intentionally does not decide them.
3. **Apply bounds to delivery of observation receipts as well as their snapshot.** The proposed 5-second dynamic TTL, 128/4096 pending limits and byte budget are reviewable defaults, not acceptance evidence. A b1 contract should also prevent a new unbounded receipt channel/closed-generation backlog and define overflow invalidation plus monotonic-clock boundary tests. This does not require b1 to fix every existing SDK/history buffer under I06; it prevents the new observation layer from adding another one.

None of these recommendations authorizes implicit probes, a native-positive capability fallback, arbitrary error-substring classification, raw provider/account diagnostics or resetting an existing uncertainty fence.

## Verification limits

Only the review document was written. `git diff --check` passed. No build, test suite, dependency installation, native process/account/history access, production service operation or Actions mutation was performed for this design review. The concurrently observed successful Checks run for source `aacaa19` validates that existing source's CI, not the unimplemented observation proposal.

Before accepting b1 implementation, independent fake-only tests must demonstrate single creation qualification, canceled setup cleanup, old actor/event/approval/exited suppression, initial attach qualification, peer reconnection and repeated ready-client invalidation, no input replay, expiry/clock/overflow behavior, scope-first pure reads and retained existing guards. Positive per-topology native readiness, typed HTTP delivery integration, unified Web activation and real native/platform acceptance remain separate gates.
