# 桌面与 Android 登录恢复

2026-11-16 用户明确要求客户端和手机保存登录、重启不再二次登录。本页替代现有文档中的应用 grant 仅内存、每次启动重新登录约定；实现与实际验收状态见[本轮任务](plan/tasks/desktop-mobile-session-recovery.md)。历史验收保留，不作为新恢复功能通过证据。

## 保存与恢复边界

Native 是唯一凭据与刷新所有者。桌面使用操作系统安全凭据存储；Android 使用 Keystore 保护的加密应用私有存储。不能把 refresh/access token 放入普通配置、日志、网页 localStorage 或返回 UI。仅保存恢复 OAuth 授权所必需的资料；Noise 私钥、协调注册密钥、活动连接和业务内容不因保存登录而持久化。

保存记录使用新 schema，并绑定完整公开授权配置。不同 issuer、client、resource、product 或配置不能互相采用凭据。不读取早期历史版本的凭据记录。恢复后必须重新验证授权与账号身份，使用新的运行期 epoch 栅栏，使旧登录、刷新、退出和连接结果不能覆盖当前状态。账号草稿和信任仍按已验证账号隔离。

启动先显示“正在恢复登录”，有有效保存授权时恢复账号，再按当前本地准备/默认远程规则继续。没有保存授权才显示登录入口。临时离线或安全存储暂不可用应显示可重试状态，不把网络故障伪装成账号退出或删除可恢复授权。授权撤销、明确 invalid_grant 或无效绑定不能当作已登录。恢复失败不能无限 loading。

刷新串行进行。新的轮换必须先安全保存，才允许后续采用；请求结果未知或保存中断不能在重启后盲目重复提交旧 refresh token。实现应提供可审查的中断/未知结果处理。安全存储写入失败要明确报告，不声称已保存。

显式退出清除本应用的保存授权并结束运行期连接；即便远程撤销失败，也必须防止下次启动重新采用被退出的授权，并准确报告撤销结果。普通关闭应用保留登录；关闭远程只影响远程连接。系统清除数据、凭据丢失或身份提供方要求重新认证时仍可能需要再次登录。

新进程恢复成功后，按当前默认策略在本地就绪时尝试开启远程一次；旧进程内手动关闭的意图不新增跨进程保存。现有 Windows Native 账号不支持的范围不因增加安全存储库而变为支持；应保留准确的支持说明。

## 界面状态

```text
启动 → 读取安全记录 → 无记录 → 登录 / 注册
             │
             └→ 正在恢复登录 → 已验证账号 → 工作区 / 我的设备
                         │
                         ├→ 临时失败 → 重试恢复 / 退出账号
                         └→ 授权失效 → 重新登录
```

桌面与 Android 的账号说明应改为保存登录，不能继续承诺“关闭即丢失授权”。恢复时不打开额外登录页面。不能以 IdP cookie 仍有效替代安全保存的应用授权。

## 验证

分别验证首次登录保存、进程重启恢复、轮换后恢复、退出后重启不恢复、配置不匹配、损坏/不可用存储、明确授权失效、临时离线和刷新/保存中断。使用隔离存储与账号夹具，不读取真实用户的凭据验证实现。浏览器夹具与 APK/真实平台安全存储验收分开记录。
