# Conditional text-file saves — I04 candidate

Status: isolated implementation candidate, not independently accepted or merged. This document records the proposed contract and evidence, not a claim that I04 is resolved.

## HTTP contract

`GET /api/sessions/:id/files?path=...` returns `{ "content": "...", "revision": "sha256:<64 lowercase hex>" }` for a UTF-8 regular file. The digest identifies the exact bytes read, including CRLF and trailing newline. Text preview and save are limited to 2 MiB.

`PUT /api/sessions/:id/files` accepts `{ "path": "...", "content": "...", "expected_revision": "sha256:..." }`. The expected digest must match the current bytes. Explicit `expected_revision: null` means create only; it never replaces an existing file. Missing preconditions return HTTP 428 with `code: file_revision_required` and an actionable upgrade/refresh message. Unknown fields and malformed digests are rejected. No legacy unconditional-write fallback exists.

A mismatch, deletion of a previously read file, or create collision returns HTTP 409 with `code: file_revision_conflict`. Success returns `{ "ok": true, "revision": "sha256:..." }`. Clients must use this returned revision as the next baseline. Existing integration/browser fixture callers now explicitly request create-only for their newly created files.

Save errors use `{ "error": "...", "code": "...", "delivery_state": "not_written" | "uncertain" }`. A replacement error or failed parent-directory synchronization returns 503 `file_save_uncertain`; the client must compare the current file rather than blindly replaying the write. A lost response or worker failure likewise requires comparison even if no structured uncertainty is available.

## Publication and boundaries

Within one AnyWork server process, all text-file writes share one publication mutex across sessions, workspaces and path spellings. The original per-path mutex failed to coordinate case-equivalent basenames on macOS; this is an AnyWork lost-update defect, distinct from the external-writer limitation below. The replacement deliberately does not guess filename identity by lowercasing or Unicode normalization. A global lock covers host filesystem case/Unicode aliases and canonical parent aliases, including absent create destinations. It is acquired before parent resolution and held through checks, temporary writes, publication and directory sync. The throughput tradeoff is that saves to unrelated files also wait for each other, including their filesystem sync latency. Given the 2 MiB editor limit, this correctness-first policy is preferable to platform-specific identity guesses; a future finer-grained strategy needs independent alias/creation/rename evidence. The server checks the expected bytes, writes a unique same-directory temporary file, preserves the existing file's permission bits, synchronizes the temporary file, checks current bytes again, and publishes it. Existing files use filesystem rename replacement. Create-only uses an atomic hard link into the absent destination; unsupported filesystems fail rather than falling back to a destructive operation. Temporary files are removed on normal failure paths.

Save rejects final symbolic links and non-regular files; parent resolution retains the session workspace boundary. Unix file opens use no-follow/nonblocking flags. Windows uses an open-reparse-point flag. There is no unlink-before-replace or truncate-original fallback. Replacement changes inode identity, so hard-linked aliases do not retain shared content. Ownership, ACLs, extended attributes, resource forks and custom security labels are not copied; only ordinary permissions are preserved. Crash termination can leave an unreferenced `.anywork-save-*` file.

On Unix, successful publication is followed by parent-directory fsync. Windows has no portable directory-fsync equivalent in this implementation, so equivalent crash durability has not been established. Replacement and hard-link semantics still depend on the host filesystem. Windows and Linux execution remain unverified; macOS is the tested host.

This is **not atomic compare-and-swap against arbitrary external writers**. A native editor or Agent that does not share the AnyWork mutex can still write between the final comparison and rename. External mutation of parent directories, mount points or hard-linked aliases is also outside this guarantee. A digest cannot detect a change that returns to identical bytes. Multiple AnyWork server processes do not share the mutex. Stronger cross-process ownership/locking would require a separate protocol and cooperation from those writers.

## Web behavior

The editor retains its draft after conflicts, transport failures, malformed success responses and uncertain results. A save response establishes a baseline only when `ok === true` and `revision` is a string matching `^sha256:[0-9a-f]{64}$`. Initial reads and comparison responses also require a revision in that exact format; comparison additionally requires string content. Truthy invalid digests, non-string revisions and false/missing/non-boolean `ok` never mark text clean. The copy/save toolbar occupies its own row above conflict notices, including the workbench layout. It offers copying the draft, fetching and comparing the latest file, explicitly adopting that revision while keeping the draft, or explicitly discarding the draft and loading the latest content. Ordinary save retries keep the original expected revision until the user selects a new baseline; comparison alone does not silently enable overwrite.

A successful save marks only the captured submitted text as saved. Text typed during the pending request stays dirty. Save/compare responses are ignored when their file, session, API instance or view generation no longer matches, including switching away and back or refreshing the same file. A legacy server without revision support disables saving and asks for an upgrade. Draft persistence across intentionally closing a file, navigation, browser reload or process crash is not provided by this candidate.

## Verification evidence and remaining acceptance

Executed in the isolated `codex/improve-file-consistency` worktree, without changing production assets or running native Agents:

- `cargo check --locked -p anywork`: passed.
- `cargo test --locked -p anywork files::tests -- --nocapture`: 9 passed. Cases cover missing/null/hash preconditions, exact byte revisions, stale-save conflicts, concurrent AnyWork saves, create collisions, injected prepublication failure, late external changes before the final check, large/special files, Unix permissions, symbolic links, FIFO and workspace traversal. The ninth case deterministically injects a directory-sync failure after successful publication, for both creation and replacement: response is 503 `file_save_uncertain`/`delivery_state: uncertain`, published bytes remain, temporary files are removed, and a create-only retry conflicts. The private synchronous helper accepts the injected sync operation; production always uses its actual platform sync operation, with no runtime fault-injection option.
- `cargo clippy --locked -p anywork --all-targets -- -D warnings`: passed.
- `cargo build --locked -p anywork`: passed.
- Web TypeScript typecheck and production build: passed, using this worktree's `web/dist`.
- `python3 scripts/file-consistency-test.py`: 6 real authenticated HTTP tests passed. These start only a temporary server on an ephemeral loopback port, with isolated workspace/data/plugins/account directories. Assertions cover the JSON revision/428/409 contract, malformed body rejection, missing/invalid preconditions, create-only races, concurrent writes across sessions and canonical parent aliases, exact Unicode/CRLF bytes, deleted files, permissions, path/symlink/type/size limits, authorization and temporary-file cleanup. Two added alias cases first confirm actual same-file identity on the temporary host filesystem; they skip with an explicit reason on filesystems where the names differ. On the tested macOS filesystem both case aliases (`case-race.txt`/`CASE-RACE.TXT`) and NFC/NFD Unicode aliases (`café-race.txt`/`café-race.txt`) were equivalent and both tests executed without skipping. Each executes ten barrier-released concurrent 512 KiB same-revision overwrite races, asserting exactly one 200 and one 409, exact accepted winner bytes and no temporary files. Each also checks concurrent create-only alias publication. The fixture creates no native Agent tasks.
- `python3 scripts/integration-test.py`: all 25 existing isolated HTTP integration tests passed, including the updated create-only caller.
- `PLAYWRIGHT_CHANNEL=chrome ANYWORK_E2E_PORT=3284 ANYWORK_E2E_OUTPUT_DIR=test-results-file-fix npx playwright test e2e/file-consistency.spec.ts e2e/conversation.spec.ts`: 21 passed, 1 intentionally skipped (the existing reference screenshot case is desktop only). All 18 file-consistency browser cases passed across Desktop Chrome and Pixel 7 emulation. They use the real isolated backend and delayed responses to cover conflict draft retention, copying, comparison, explicit rebasing/reloading, edits during a pending save, file/session switching, A→B→A comparison generations, malformed success and transport failure. Follow-up negative cases include the independently reproduced `{ok:false,revision:"invalid-but-truthy"}`, valid-format revision with false/missing/non-boolean `ok`, non-string/uppercase/invalid revision values, null response, and invalid comparison revisions. They assert the draft remains dirty, disk bytes remain unchanged and the original valid revision still permits a real save. A simulated post-publication 503 response verifies comparison and explicit baseline adoption instead of a false clean state. The conflict tests assert the toolbar's bottom does not overlap the banner's top on either viewport. Three existing conversation/document cases also passed.

The HTTP script can use `ANYWORK_BINARY` to select an independently built candidate. Browser tests use the existing isolated `scripts/e2e-server.py`, the worktree's own target and Web output, and a dedicated port; they never connect to production port 3210. Clipboard writing is stubbed in the browser test so draft-copy assertions do not depend on host clipboard permissions. Native Agent applications/accounts and production assets were untouched. Registering the new script in shared `scripts/check.sh` remains the integrating owner's responsibility.

Not yet accepted: Linux/Windows behavior, network filesystems, physical Android/browser devices, actual power-loss/kernel/fsync failures and an independent exact-follow-up-commit review. Post-publication fault handling is now covered through deterministic helper injection plus browser error-response simulation; this does not establish actual crash durability or arbitrary external-writer CAS.
