# 给 CyberGrid 开发组的集成反馈与改进要求

日期：2026-11-10。反馈方：AnyWork 使用者与集成方。用途：在 AnyWork 统一桌面、Web、手机连接体验之前，与 CyberGrid 开发组讨论能力边界、接口和交付顺序。本文件可独立转发，不包含部署凭据、个人账号或用户业务数据。

调研基线：CyberGrid 主分支 [`50a12e0d7b58e3f8dd84b9d9a97fe650faaac691`](https://github.com/ywateru/CyberGrid/tree/50a12e0d7b58e3f8dd84b9d9a97fe650faaac691)。AnyWork 当前固定集成 `2bd6729`；两者之间仅有部署/验收说明及其静态文档页面变化，SDK、协议、服务运行代码和 getting-started 流程没有变化。以下明确区分现有能力、实际使用问题与建议新增能力，不把建议描述为已交付承诺。

## 2026-11-11 补充：协调存储额度与可观测性

正式集成的公开配置接口返回 HTTP503 / `COORDINATOR_UNAVAILABLE`；真实 Rust SDK 与 Native HTTP 路径均重现。Upstash 独立只读核查得到固定错误 `max requests limit exceeded`，计数500030，免费上限500000。管理信息仍显示 active，PING/TYPE可用，因此基础连通性不能替代业务协调操作就绪检查。这是本次观察到的供应商额度故障，不是对历史所有配置失败的归因。

建议补充以下要求用于开发组评审：

- 给出持续在线设备、心跳、目录查询、信令长轮询对应的 Redis 命令成本模型，以及单设备每天的参考消耗；免费额度不可被当作持续运行容量承诺。
- 健康探针验证真正依赖的存储操作权限和额度，并区分存储容量、请求额度、限流、鉴权与传输故障；对外只返回固定安全分类，不回显供应商凭据或用户内容。
- 提供可观察的额度/剩余额度告警和恢复指引。长期协调不可用时有限退避，不让所有客户端重试放大消耗；任何优化必须保持租约、代际隔离、撤销和恢复正确性。
- 说明免费与按量方案适用边界；套餐变更、迁移或重置不得由 SDK 静默执行。保留 namespace/epoch，不为恢复服务而清空现有协调材料。

AnyWork本轮产品策略也已按使用者要求修订：每次登录且本地服务就绪后默认尝试开启远程，手动关闭在当前登录会话保持。下文2026-11-10的原始产品描述保留为当时反馈背景，现行行为以[桌面启动契约](desktop-onboarding-layout.md)为准。

## 1. 作为使用者，我们希望怎样使用

> 我打开电脑上的 AnyWork，就能在本机浏览器使用。需要出门继续工作时，在电脑上登录并允许远程访问；然后在网页或手机上登录同一个账号，选择这台电脑就能继续。整个过程不需要知道地址、端口、隧道或 WireGuard，也不需要复制访问令牌。网络变化、令牌正常续期和底层线路选择，应由软件处理。

目标是访问电脑上的 AnyWork 工作区：会话、Agent、文件、事件与终端。此处不把操作系统屏幕投送、鼠标键盘远控或通用 RDP 作为本轮需求。

```text
电脑上的 AnyWork
  ├─ 本地工作区                           [在浏览器打开]
  │    └─ 本机服务可用时即可使用，不依赖云服务登录
  └─ 账号                                 [注册 / 登录]
       └─ 允许我的其他设备访问             [开启 / 关闭]
            └─ 这台电脑：可连接 / 准备中 / 需要处理

远程网页 / 手机浏览器
  └─ 注册或登录同一账号
       └─ 我的设备
            └─ 选择电脑 → 验证设备身份 → 打开同一个工作区
                 └─ 网络中断时显示恢复进度，不要求输入新地址
```

普通用户只面对“账号、电脑、工作区”。AnyWork 计划移除现有独立的匿名隧道、固定隧道、WireGuard 配置及手动地址/令牌连接流程，使用账号连接作为统一远程入口。CyberGrid 内部可以采用不同传输或中继，但这些是实现细节，不能再次成为需要用户选择和维护的连接方式。

本地使用和远程授权是两个动作。登录不应静默公开本机工作区；首次启用远程访问须有清楚的本机授权。远程关闭后，本地工作仍可继续。

桌面已经登录时，本地Web也应在受限本机会话中识别同一账号和当前电脑，避免要求再配置一份连接或手动复制令牌；这不表示向本地浏览器转交Native刷新凭据。离线或未登录时仍能打开本地工作区。

## 2. 现有集成反馈

整体注册、登录、设备发现和远程访问已经跑通。现在主要问题是不同入口和生命周期之间缺少统一体验，接入方还需要自己拼接较多逻辑。

| 使用感受 / 观察 | 技术归属与证据边界 | 对开发组的反馈 |
| --- | --- | --- |
| 桌面仍展示多种隧道，网页有账号入口和高级连接，手机又有手动配置，难以知道应该走哪条路径。 | 首先是 AnyWork 产品入口与迁移问题，不能归为 CyberGrid 缺陷。 | 希望 SDK 能支持稳定的“发布本机工作区 / 连接账号设备”抽象，让产品无需暴露线路配置。 |
| 同账号登录成功后，用户预期立刻看见电脑；实际还取决于远程授权、设备发布和目录同步。 | 登录、在线心跳、端口发布、业务授权是不同阶段。 | 需要可观察的统一状态和原因，不能只给一个 `online` 值或 URL。 |
| 曾出现配置校验失败，稍后手动重试成功。 | 当前公开绑定检查通过；未获得当时完整请求轨迹，不能断定是配置内容错误。原接入错误分类较粗。 | 配置错误与暂时网络/服务故障应可区分，并给出安全、有限的恢复策略。 |
| 远程工作区曾频繁提示授权过期。 | 已确认是 AnyWork 自建浏览器业务通道使用最多300秒授权且未续期；Logto缓存令牌剩余时间也会影响时长。不是已证实的 CyberGrid 业务通道续期缺陷。 | 如上游提供浏览器安全通道，应把短期授权的持续更新列为完整契约；若仍由接入方实现，也应提供参考与边界说明。 |
| 原生 SDK 和 Web SDK 的能力不对称。 | Rust已有原生安全传输；JS目前明确是只读目录 SDK。 | Web与手机浏览器要达到同等体验，需要浏览器业务连接能力，或稳定且明确的外部安全通道扩展点。 |

此前图片缺失属于 AnyWork 静态部署路径错误，不作为 CyberGrid 改进要求。也不要求 CyberGrid 理解 Agent、会话、业务请求或终端语义。

## 3. 已有能力请保留，不需要重复建设

当前上游已经具备以下基础，建议继续作为兼容基线：

- Logto 同账号、同 Native 应用设备发现；SPA只读查询所选 Native 应用下的设备和端口。
- Rust SDK 的 WebRTC → iroh直连 → Cloudflare回退，以及可选并行直连；原生流使用内层双向TLS。
- 心跳、65秒租约、epoch、注册/发布代际约束、自动单飞协调恢复、provider事件和有限资源约束。
- JS SDK 的宿主 `getAccessToken` 回调、严格 issuer/client/resource 绑定、取消、同身份恢复和固定错误码。
- Vercel / Docker 部署与 Redis / Upstash 共享协调，不依靠单进程内存作为生产状态。

需要特别区分三种时间：CyberGrid协调session当前为24小时、设备在线租约为65秒（通常每20秒心跳），AnyWork原浏览器业务授权最长为300秒。已有协调恢复会重新注册并恢复发布意图/映射监听；已中断的旧TCP流不因此无缝恢复。这三种生命周期需要分别验收。

我们希望在这些基础上补齐产品集成，而非另外建设一套账号系统、业务数据库或内容代理。

## 4. 职责与安全边界

| 层次 | 负责 | 不应承担 |
| --- | --- | --- |
| Logto | 注册登录、账号授权、用户偏好与最少持久设备配置；支持自部署。 | 会话正文、文件、终端历史；把频繁心跳当账号配置写入。 |
| CyberGrid | 同账号设备发现、在线与发布状态、信令、连接协商、SDK恢复；Upstash保存必要协调元数据。 | 存储或解密业务内容；代替桌面决定工作区访问权；向客户端下发管理密钥。 |
| AnyWork桌面 | 本地服务、明确远程授权、工作区权限、设备身份验证、关闭与本机业务执行。 | 因为用户知道一个URL就放行业务；把本机长期访问令牌上传云端。 |
| AnyWork Web / 手机 | 账号入口、设备列表、身份确认、工作区UI与业务恢复语义。 | 假定“在线”等于已授权；不经确认重放发送消息、执行命令、提交文件等写操作。 |

业务内容和端到端解密密钥只在用户设备上。第三方中继如承载业务字节，只能传送端到端密文；Cloudflare外层TLS不能代替端到端加密。运营侧仍会接触身份和必要连接元数据，不能宣传整个系统“零用户数据”。

首次设备公钥发现仍依赖账号目录的完整性；托管Web代码也属于可信执行边界。端到端加密不能消除恶意前端脚本的风险，因此需要明确首次确认、换钥提示和前端发布供应链的责任。

不新增 AnyWork 云端业务数据库、票据服务或长期内容缓存。日志和故障报告应有固定字段与脱敏约束，不包含OAuth令牌、私钥、带凭据的URL、文件路径或业务正文。

## 5. 请求 CyberGrid 优先支持的能力

下表的 P0 是统一正式远程体验所需的契约，P1 是规模化与长期维护要求；先由开发组确认方案及可行性，再排期。接口名字均为讨论用，不是现有 API。

| 编号 | 优先级 | 要求 | 期望交付与验收 |
| --- | --- | --- | --- |
| CG-01 | P0 | **面向浏览器的安全连接契约。** 提供可在桌面浏览器及手机浏览器运行的端到端加密双向流；或正式定义让 AnyWork 接入自有安全通道的扩展接口。 | 明确设备身份绑定、同账号业务授权、取消、流控、最大帧/流数、密钥与会话关闭语义。浏览器不能把设备级 `tunnelUrl` 当HTTP入口；不支持时返回明确能力状态。不得自动退回明文业务。 |
| CG-02 | P0 | **把用户会话和协调会话分开，支持持续授权。** 宿主持有Logto刷新权，SDK按需获取足够新鲜的资源令牌。 | 明确token回调的 `minValidity` / 强制刷新需求及失败语义，保持单一刷新所有者；短期授权正常续期不强制离开工作区。新授权必须同subject、issuer、audience、允许client、scope并有效，不能单纯延长TTL。未知轮换结果不重放旧grant。 |
| CG-03 | P0 | **统一可观察状态。** 分开身份、协调、设备发布、可达性、业务授权。 | 提供可订阅快照/事件及稳定原因码，能区分“已登录未开启”“发布中”“可尝试连接”“正在恢复”“需重新登录”“配置不匹配”“服务暂不可用”。`ready`应表明具体就绪层级，不能只代表提交已受理。 |
| CG-04 | P0 | **明确一个产品的SPA与Native绑定。** 浏览器、桌面和未来原生手机可以使用各自正确类型的Logto应用，同时属于同一AnyWork产品。 | 支持管理员显式允许的SPA/Native集合和版本化公开配置，不让用户选择租户全部应用。保留client/issuer/resource/scope严格验证及跨账号隔离；不以取消client检查实现互通。 |
| CG-05 | P0 | **可预测的恢复与取消。** 复用已有协调恢复，覆盖断网、切网、电脑休眠、移动浏览器挂起和provider退出。 | 暴露恢复阶段、可重试性和总预算；旧epoch/代际的迟到响应不能复活旧连接。已断TCP/PTY是否能恢复须明确，不能承诺字节流无缝续传。停止自动重放业务写入；取消后不再悄悄发布或连接。 |
| CG-06 | P0 | **可用于正式产品的入口/provider契约。** 现有端口URL限制为trycloudflare根地址，Quick Tunnel没有生产可用性保证。 | 给出生产支持路线：可由部署者配置稳定入口、受支持provider或其他可用传输，并说明平台、配额、时延与失败限制。入口由产品配置，不要求最终用户创建隧道。新增域名需显式信任策略，不能无约束接受任意URL。 |
| CG-07 | P1 | **统一逻辑设备身份与进程身份。** 区分稳定安装ID、当前Grid注册ID、运行代际及加密公钥。 | 提供宿主公开安装ID的安全关联/查找契约，服务端按验证后的owner/app限定命名空间；安装ID本身不构成授权。支持明确的RAM-only模式，不强制持久化注册私钥。重复启停不无限新增用户可见设备。 |
| CG-08 | P1 | **版本化目录变化通知。** 减少接入方定时全量刷新及双目录拼接。 | 在Vercel限制内提供可取消的watch/长轮询或等价机制，给出revision、游标/重置、容量与完整性语义。在线状态与发布状态可分别变化；协调不可用显示未知。长期离线设备和别名仍由Logto配置负责，不变成第二个持久账号资产库。 |
| CG-09 | P1 | **配置校验、错误和重试标准化。** 现有固定错误码继续保留，补齐初始化依赖、重试预算和操作结果。 | 幂等配置GET可有限退避；配置不符/鉴权拒绝立即失败。注册和发布使用已有fence/idempotency机制处理不确定结果，不盲目重复操作。输出 `stage`、固定 `reason`、`retryable`、`retryAfter` / 预算等安全字段；保留本机诊断关联ID，不含秘密。 |
| CG-10 | P1 | **关闭、注销、移除与撤销各有清楚语义。** | 区分停止发布、关闭本机入口、撤销协调会话、退出Logto、隐藏设备。关闭远程先在本机禁止新连接并终止活跃远程会话，再撤回发布；云端失败时仍保持本机关闭。远程撤销须有目标确认/待确认状态及最坏生效窗口，不能把删除目录当即时撤销。 |
| CG-11 | P1 | **自部署身份服务与最小权限配置。** 当前上游getting-started要求Management API `all`读取应用目录，对业务集成偏重。 | 支持公开静态允许应用目录，或提供真正受限的应用目录接口；若仍依赖Management API，其audience可配置，不能假定为issuer origin加 `/api`。管理M2M不进入浏览器、桌面构建或业务通道；尽量不成为协调运行期依赖。 |
| CG-12 | P1 | **可维护的SDK交付与元数据生命周期。** | 发布清楚的JS/Rust/服务兼容矩阵、能力协商、迁移示例与可复现测试；明确Windows/Linux及Android/iOS/浏览器支持程度。记录Upstash各类键的用途、逻辑到期/物理清理、fence/seed保留和删除方案，并确认SDK嵌入和分发许可。 |

对于 CG-01，短期允许继续复用 AnyWork 已有的安全桥接，前提是 CyberGrid 能稳定提供目标能力、地址变化与失效事件。希望上游明确选择“提供浏览器传输”还是“正式支持安全桥接扩展”；不要求为统一UI立即重写全部底层传输，也不希望长期靠未约定的URL拼接维持。

对于 CG-04，同账号跨设备访问不等于跨账号分享。本轮不请求团队协作、访客访问或组织权限；以后增加时须另立授权模型。

## 6. 不保存本机秘密时的体验约束

AnyWork 当前明确采用进程内存保存Native账号令牌、注册私钥和业务加密私钥，不使用本地钥匙串或普通文件保存这些秘密。只持久化非敏感安装标识。

这意味着客户端退出后不能承诺“重开自动登录并自动远程可用”；重启需重新登录并重新开启远程访问。Logto系统浏览器SSO可能缩短登录，但不等于本机持有授权。新进程产生的新公钥，也不能只凭相同安装ID就静默接受。

希望 CyberGrid 提供清晰的RAM-only集成示例和身份变化事件。AnyWork负责减少重复页面跳转、展示当前步骤，并用合适的身份确认交互处理换钥；不能为了体验流畅而暗中落盘秘密或忽略公钥变化。若未来希望跨重启完全无感，应另行讨论可信设备持久凭据策略，不能作为本次默认前提。

## 7. 建议双方共同验收的场景

以下是提议的交付验收目标，尚不代表当前版本已全部通过。时延从所需前置条件满足时开始计量，应先在约定网络环境建立基线；网络不可达时报告原因和截止预算，不宣称任意网络都能满足目标。

| 场景 | 可观察的通过标准 |
| --- | --- |
| 本机独立使用 | 桌面启动本机服务后，一次点击打开本地Web；未登录、Logto或CyberGrid不可用时，本地已有工作区仍可使用，保留本机鉴权边界。 |
| 全新账号与两端登录 | 桌面注册/登录并开启远程；Web和手机浏览器独立登录同账号，无地址、端口、令牌输入。正常协调环境下，已确认发布后5秒内目录显示状态变化。 |
| 设备可见与可用区别 | 发布未完成显示准备中；配置故障显示明确原因；发现在线但业务连接未就绪时不显示已连接。没有端口URL不能用设备级URL顶替。 |
| 持续工作 | 先连续运行30分钟并跨越至少6个短授权周期，再做8小时稳定性测试、超过10,000个混合请求及活跃PTY；协调session到期则另做超过24小时或等价可控时钟测试。正常续期不中断业务，内存/ID去重有界，不存在小的累计请求数上限。 |
| 手机实际网络 | Android Chrome和iOS Safari分别进行Wi-Fi、蜂窝、切网、锁屏/后台再返回测试。允许平台挂起连接，但回前台必须重新确认授权和设备状态；展示恢复/重连，不能假称后台一直在线。 |
| 连接预算与取消 | 约定每个阶段及总预算；首轮建议完整尝试不超过60秒，不能无限转圈。用户取消后1秒内停止UI等待，底层异步清理有界且不能再发布迟到成功。 |
| 设备休眠、离线和协调故障 | 失去有效租约后不再保留“可连接”结论；状态收敛目标按租约与通知预算验收。协调无法访问时显示暂时未知，恢复后重新核验；本地工作不受影响。 |
| 隔离、换号与换钥 | A账号看不到/连不上B设备；退出或切号后迟到回调不能恢复A连接。过期、错issuer/audience/client/scope、旧代际、未确认换钥都被拒绝。 |
| 关闭与撤销 | 本机关闭远程后拒绝新连接，终止已有远程HTTP/PTY，本地继续工作。断网关闭也有效；隐藏目录、撤销云端会话与本机关闭分别显示真实结果。 |
| 内容与诊断边界 | 用合成数据检查协调API、Upstash字段、日志和构建产物，不出现业务正文、文件或私钥/令牌。中继只可见密文与必要网络元数据。列出仍会持久保留的协调材料及清理方式。 |

连续连接测试同时覆盖正常更新和拒绝更新。授权过期、关闭或撤销时必须及时终止业务，不能为通过稳定性测试而放宽授权。业务执行结果未知时，恢复连接不自动重发。

## 8. AnyWork 自己承担的改造

这些工作不等待上游替我们完成，也不作为 CyberGrid 缺陷：

1. 统一桌面、本地Web、远程Web和手机的账号/设备/工作区导航；正常流程移除手动地址、访问令牌和线路选择。手机浏览器优先，原生手机应用单独规划。
2. 移除桌面原有独立匿名/固定/WireGuard连接的配置、启动和监控入口，并审计相关后台生命周期。不能只隐藏按钮，留下旧的无账号公网入口继续运行。
3. 设计升级交接：先盘点旧入口及活动连接，说明切换影响，再确认账号通道就绪后停用旧独立入口；不在用户工作过程中直接杀进程，不删除会话、工作区或账号配置。底层若复用provider，也只作为账号授权通道的内部实现。
4. 本地Web继续使用受限本机访问；云端账号不能获取或公开本机长期bearer。切换本地/远程都定位同一台设备的现有工作区，不把业务复制到云端，不因重连重复创建会话。
5. 负责浏览器业务授权、当前安全桥接、短期授权更新、无重复执行的业务恢复、公钥确认和用户提示；图标/图片、PWA与响应式布局由AnyWork修正。
6. 明确“退出账号”“关闭远程”“退出客户端”的区别，适配RAM-only重启流程，并验证手机触控、返回、深链接和重新登录后的回到原位置。

验收门槛是：用户没有旧式独立远程入口可选，账号连接仍覆盖全部正式远程场景；若目标平台或生产入口尚未具备，先明确平台范围和阻塞项，不靠恢复旧无账号入口填补。

## 9. 希望开发组先答复的问题

- **浏览器路线**：是否愿意提供端到端安全流SDK？若短期不做，能否承诺安全桥接所需的能力描述、发布/失效事件及接口兼容性？
- **身份与配置**：能否提供产品级SPA/Native允许绑定、宿主逻辑安装ID关联，以及无需运行期Management `all`的配置模式？
- **生产连接**：除Quick Tunnel外，计划支持哪些正式入口/provider，谁维护、有哪些可用性与成本限制？手机Web和原生SDK是否采用不同路线？
- **生命周期**：哪些状态/恢复/持续授权由SDK保证，哪些必须交给宿主？能否提供最小RAM-only端到端示例和故障测试矩阵？
- **交付边界**：建议的API版本、兼容窗口、平台顺序、分发许可及元数据保留策略是什么？哪些P0可先交付，哪些需要替代方案？

建议先确定 CG-01～CG-06 的接口契约和责任分工，建立Mac宿主 + Web + 手机浏览器的共同样例，再推进稳定设备身份、目录通知和多平台发布。AnyWork的统一界面与旧入口退役按这些已确认契约实施。
